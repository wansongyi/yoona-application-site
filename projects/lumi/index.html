Overview

Lumi is a teacher-grounded conversational learning system for young learners. I adapted and extended a React/FastAPI AI tutoring platform into a product workflow that connects teacher-provided knowledge, retrieval-aware generation, configurable tutor behavior, evaluation, and parent-facing evidence.

The problem

A fluent chatbot can sound helpful while answering outside the teacher's curriculum, overstating what a child understands, or giving adults a false sense of evidence. Lumi treats those as product and systems problems rather than only prompt-writing problems.

Design goal: make the system useful while keeping the knowledge boundary, uncertainty, and evidence visible.

What I built

  • Teacher-facing file ingestion and knowledge-source workflow.
  • Configurable tutor behavior, personality, learning goals, and publishing flow.
  • Retrieval-aware generation boundaries and explicit unsupported-answer behavior.
  • Streaming conversational experience and child-facing practice flow.
  • Test & Compare workflows for reviewing response variants and grounding behavior.
  • Parent-facing evidence views that distinguish observed interaction from stronger claims about mastery.

System flow

Teacher source→Chunk / retrieve→Grounded response→Abstain if unsupported→Evaluation + evidence

The production architecture is more extensive: Privacy Service, separate Privacy and Learning databases, User/Bot/Chat services, pgvector-backed retrieval, asynchronous knowledge processing, Redis, RabbitMQ, object storage, and an external LLM provider.

Evaluation

Instead of treating one response as proof that the system works, Lumi includes a comparison workflow for testing configuration and response variants. The portfolio demo exposes deterministic grounding checks so a reviewer can see why a response passes or fails.

Grounded answer

Source cited · supported by teacher material · stays within curriculum boundary · age-appropriate.

Unsupported question

The tutor abstains rather than inventing an answer and suggests an appropriate next step.

Production vs. public demo

The public portfolio demo intentionally does not run the full production microservice stack. It uses sample curriculum, deterministic retrieval, reviewed response variants, and session-local state so reviewers can inspect the product logic without collecting student data or requiring paid infrastructure.

The demo is a transparent showcase of interaction and evaluation logic, not a claim that the production system has been fully deployed for real students.

What remains unproven

  • A fluent child response does not establish conceptual understanding.
  • Retrieval can fail on incomplete, off-topic, or disfluent input.
  • Adult summaries can overstate learning if evidence is not carefully scoped.
  • Child-facing deployment still requires educator review, privacy controls, and structured evaluation.
